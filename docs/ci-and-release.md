# 检查、部署与恢复设计

2026-09-21｜待工程导入后实施。本轮没有创建 `.github/workflows/`，也没有启用自动部署。

## 1. 检查分层

| 环节 | 触发方式（拟） | 检查对象 | 通过意味着什么 |
|---|---|---|---|
| 文档检查 | PR 与 main 更新 | 本地链接、元数据、公开文件范围 | 规范结构可用 |
| 构建检查 | 影响课件的 PR 与 main 更新 | 锁定环境下安装及构建 | 指定提交可以生成网页 |
| 数值与组件检查 | 相关算法或组件修改 | 固定样本、重置、参数边界、失败例 | 受测行为与预期一致 |
| 浏览器检查 | 相关交互与布局修改 | 导航、页面、演讲者模式、资源请求 | 受测设备与场景可操作 |
| 内容审读 | 案例、解释或来源变化 | 原页、支持范围、概念与教学任务 | 经审读版本可用于相应教学 |
| 发布检查 | 发布前 | 全站包、课堂设备、备用路径 | 此版本可作为本次课堂发布候选 |

构建成功不能证明史料真实；课堂截图不能证明数值算法正确。每条结果须写运行日期、源码提交、环境、步骤和结论。没有执行的检查保留“未执行”。

导入后拟使用 `docs-check`、`build-week03` 等稳定检查名；实际实现并成功运行后再加入主线必需检查。若采用路径过滤，必需检查仍须返回明确结果，避免未触发的工作流永久等待。

## 2. 构建约定

保留助教工程声明的 `pnpm@10.10.0` 与锁文件作为初始核对对象。正式复现时选择依赖支持的 Node LTS 并锁定实际版本；当前 shell 没有解析到 `node`，不能声称环境已经就绪。

后续在 `apps/week03/` 内预计采用：

```sh
pnpm install --frozen-lockfile
pnpm build
```

这些命令来自输入工程的脚本声明，尚未运行。本轮不执行 skill 的 `create-deck-project.mjs`；它会复制模板并立即安装依赖，不适合覆盖助教已修改的工程。

`www/` 是待核对的网站构建产物，`dist/` 是组件分发产物，不能默认二者都部署。输入还含 `build:dsh-preview`；其中预置资源的生成来源、所需上游目录和是否可重复构建须在 P2 核对，不能因 ZIP 附了编译文件便视为完整复现。

建议 CI 使用 GitHub 官方 Actions；启用时核对支持版本并固定可追溯引用。普通 PR 检查仅给读权限，不提供课堂 API 凭据，不把来自 PR 的代码交给具有部署权限的流程执行。

## 3. 浏览器和教学数据验收

- **导航**：前后翻页、总览、稳定页面 ID、全屏；输入框或正则编辑时方向键不意外翻页。
- **双屏**：打开演讲者视图、观众窗口同步、计时、备注、关闭后重新连接。
- **数据**：切换案例后清空上一案例的查询和结果；原文保持只读；固定输入得到可解释的排名；至少一个无依据问题。
- **模式**：页面分别说明嵌入、检索和生成是实时、预计算、预存输出还是教学构造。
- **设备**：课堂实际投影尺寸、常用浏览器、小屏和低功耗；记录实际结果，不预先许诺响应速度。
- **联网与备用**：网络超时、模型不可用、无账号、首次访问与已有缓存分别检查。离线使用静态结果或本地 HTTP 包；不能把有远程字体、模型或接口的页面直接宣称完全离线。
- **浏览器资源**：核对 WASM、Worker、字体、模型文件、跨域请求；需要跨源隔离的候选组件先独立试验，确认目标托管是否满足条件。

学术来源状态（已核／待核／教学构造）与软件状态（未测／可运行／课堂验证）分列。两者不能相互代替。

## 4. 发布管线

建议采用 GitHub Pages 的 **Actions 构建产物发布**，不提交编译目录到主线，也不维护一条人工复制产物的 `gh-pages` 分支。Pages 提供静态托管；模型 API、检索服务与桌面客户端另有运行环境。[GitHub Pages 的用途和边界](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

拟设置：

| 配置项 | 建议值或行为 |
|---|---|
| Pages 来源 | GitHub Actions，首次有可部署工程时再启用 |
| 发布触发 | `workflow_dispatch` 手动触发；仅接受 main 上的运行 |
| 发布对象 | 触发时确定的 `github.sha`，所有检查与产物绑定这一提交 |
| 作业顺序 | 构建并检查 → 组装完整站点 → 上传 Pages artifact → 部署 |
| 部署环境 | `github-pages`，只允许 main；若设置环境审批，指定实际发布人 |
| 权限 | 普通构建 `contents: read`；仅部署作业增加 `pages: write`、`id-token: write` |
| 并发 | 统一 Pages 发布组，正式部署期间不被新请求中断；候选版本可排队 |
| 发布范围 | 仅 `site/` 中明确允许公开的文件 |
| 记录 | 构建提交、Actions run、产物校验值、线上 URL、发布人及上一可用版本 |

GitHub 官方要求 Pages 部署使用相应权限、构建依赖与部署环境。本表是在此基础上的本项目设计，尚非已生效设置。[Pages 自定义工作流](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)

环境审批和分支限制需要在 GitHub 中实际配置，文件里写出环境名不会自动建立全部保护规则。不要把用户已给出的发布授权拆成反复的聊天确认；平台审批如已配置，则由指定发布人在实际发布步骤完成。[部署环境说明](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)

建议路由为 `/pku-aihis/week03/`；这只是规划，实际地址以部署返回值为准。组装后应有 `site/week03/index.html`，资源相对该周目录加载。须在项目子路径下测试，尤其防止 `/build/`、`/assets/` 误指向域名根目录。

**每次发布组装完整网站。** 若已发布第二周，第三周上线时必须同时保留第二周产物；不能把仅含第三周的目录上传后覆盖整个站点。建立明确的发布周次清单，按清单构建或复用有校验记录的产物。每次部署后抽查所有已发布周次的入口。

PR 阶段以本地预览和 Actions 构建附件为主。需要公开预览时另设经过确认的预览目的地；GitHub Pages 正式站不作为各分支互相覆盖的临时预览区。公开仓库的 PR 附件同样不应包含私人输入。

## 5. 正式版本与课堂冻结

建议标签形如 `week03-2026-09-24-v1`；只有在对应提交验收通过、上线核对成功后才登记正式发布，不预先创建空标签。冻结时间由授课安排确定，冻结后仅处理影响课堂的必要修复，普通改动放下一版本。

发布记录必须能回答：本次讲的是哪一份源码、哪些数据和模型版本、哪些功能依赖联网、断网时怎么继续、上一个可用版本是什么。下载的课堂包应有简短启动说明，并通过实际离线或断网场景检查。

## 6. 发现问题后怎样恢复

1. 记录故障、受影响周次、线上提交与发生条件；课堂先使用已验证的备用包。
2. 对回归故障，在修复分支对相关主线提交做 `git revert` 或最小修复，保留历史。通过必要检查后经 PR 合入 main。
3. 从恢复后的 main 重新生成**完整站点**，按同一手动发布流程上线；核对其他周次没有丢失。
4. 记录恢复提交、新的部署记录、恢复到的功能状态。旧标签保留，不移动、不强推 main。

Actions 的“重新运行旧工作流”只有在所需依赖与产物可用、目标版本已核对时才可能成为应急选项，不能保证必然恢复。默认恢复办法是可审阅的撤销提交与重新部署。
